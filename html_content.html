HTML vs. Markdown for Agent Output

Notes from Thariq Shihipar's article, adapted to the AgentBoard context. The same content as html_content.md, written in the medium it argues for.

Provisional verdict

Don't switch the dashboard's storage format. Do start producing companion HTML artifacts for long-form, read-once content aimed at humans outside the repo. Revisit after a month of usage.

The thesis

As agents do more of the writing, the value of "human-editable plaintext" drops and the value of "human-readable rich document" rises. The original argument for Markdown was "a human should be able to edit this in any text editor." That argument decays the moment the human stops editing the doc directly and starts prompting the agent to edit it. At that point the only remaining job of the format is to be read — and HTML reads better.

When each format wins

HTML's territory

  • Specs, plans, design explorations (the web of artifacts)
  • PR explainers with diff + annotations + flowcharts
  • Research reports synthesizing Slack + git + codebase
  • Throwaway editors with "copy as JSON" exits
  • Anything you want a non-engineer to actually read

Markdown's territory

  • Specs reviewed in git PR diffs
  • Docs edited frequently by hand
  • Short reference notes (< ~100 lines)
  • Files an LLM has to read often — token cost matters
  • READMEs, ROADMAPs, CHANGELOGs

The decision flow

Five use cases worth trying

Specs & exploration

Instead of one PLAN.md, generate a web of HTML files: brainstorm grid → mockups → final plan. Pass them all into a fresh session for implementation.

PR explainers

Render the diff with inline annotations, color-coded severity, flowcharts. Attach to every PR. Beats GitHub's diff view.

Design prototypes

HTML is design's lingua franca even when the target is React/Swift. Add sliders so you can tune without re-prompting.

Research reports

Synthesis across Slack + codebase + git + web → one readable HTML explainer with SVG diagrams. Send to leadership.

Throwaway editors

Purpose-built single-HTML UI for one piece of data — drag tickets between columns, tune a system prompt. Always ends with a "copy as JSON" / "copy as prompt" button.

How to start

Don't build a /html skill. Just prompt:

make an HTML file that <does X>
make an HTML artifact that <explains Y>

For taste/styling: have Claude read your codebase and generate one design-system.html reference file, then point future generations at it.

Implications for AgentBoard specifically

The dashboard already renders MDX with React components. The viewer-side richness Thariq wants from HTML, we get from MDX + components — a <MetricCard> is richer than a hand-rolled <div style>. And specs (spec.md, ROADMAP.md, CORE_GUIDELINES.md) live in git and get reviewed in PRs, where HTML diffs would be unreviewable.

Concretely worth trying:

  • When an agent writes a long-form explainer (>200 lines) for a human reader, generate both the MDX dashboard page and a standalone .html file for sharing externally / reading on mobile / sending to non-technical stakeholders (the §5 audience the project optimizes for).
  • Keep specs and roadmap as .md — diff-reviewed, frequently hand-edited.
  • Skip "throwaway editors" for now; built-in components cover most of those use cases.
